# @Transactional — AOP 관점에서의 동작 원리

## 1. AOP(Aspect-Oriented Programming)란

비즈니스 로직(핵심 관심사)과 횡단 관심사(Cross-Cutting Concern)를 분리하는 프로그래밍 패러다임.

**횡단 관심사**: 트랜잭션, 로깅, 보안, 캐싱 — 여러 레이어에 걸쳐 반복되는 코드.

`@Transactional`은 AOP의 대표적인 적용 사례. 비즈니스 로직에 트랜잭션 코드를 직접 박지 않고, 선언만으로 끼워넣는다.

---

## 2. Spring의 AOP 구현 방식 — 프록시 패턴

Spring AOP는 **런타임 프록시** 기반이다. 컴파일 타임이 아니라 런타임에 프록시 객체를 생성해서 원본 빈을 감싼다.

### 프록시 생성 방식 두 가지

| 방식 | 조건 | 원리 |
|------|------|------|
| **JDK Dynamic Proxy** | 인터페이스 있을 때 | `java.lang.reflect.Proxy`로 인터페이스 구현체 생성 |
| **CGLIB Proxy** | 인터페이스 없을 때 (기본값) | 바이트코드 조작으로 클래스 상속 후 메서드 오버라이드 |

Spring Boot는 기본적으로 인터페이스 유무와 관계없이 **CGLIB**를 쓴다 (`spring.aop.proxy-target-class=true` 기본값).

### CGLIB 동작

```
원본: PostService
CGLIB가 생성: PostService$$EnhancerBySpringCGLIB$$abc123 extends PostService
```

컨테이너에 등록되는 빈은 원본이 아니라 이 서브클래스 프록시다.

---

## 3. @Transactional의 실제 처리 흐름

```
Client → PostServiceProxy(CGLIB) → TransactionInterceptor → PostService(실제 코드)
```

`TransactionInterceptor`가 핵심. `MethodInterceptor`를 구현하며 실제로 아래를 수행한다:

```
1. PlatformTransactionManager.getTransaction()  // 트랜잭션 시작 or 기존 참여
2. 실제 메서드 invoke
3. 정상 → commit()
4. 예외 → rollback() (기본: RuntimeException, Error만)
```

---

## 4. 트랜잭션 전파(Propagation)

현재 트랜잭션이 있을 때 새 트랜잭션을 어떻게 처리할지 정책.

| 옵션 | 동작 |
|------|------|
| `REQUIRED` (기본값) | 있으면 참여, 없으면 새로 시작 |
| `REQUIRES_NEW` | 항상 새로 시작. 기존 트랜잭션 일시 중단 |
| `NESTED` | 중첩 트랜잭션 (savepoint). 내부 롤백이 외부에 영향 안 줌 |
| `SUPPORTS` | 있으면 참여, 없으면 트랜잭션 없이 실행 |
| `MANDATORY` | 반드시 기존 트랜잭션 있어야 함. 없으면 예외 |
| `NEVER` | 트랜잭션 없어야 함. 있으면 예외 |
| `NOT_SUPPORTED` | 트랜잭션 없이 실행. 기존 트랜잭션 일시 중단 |

실무에서 가장 자주 보는 실수: `REQUIRES_NEW`를 같은 클래스 내에서 호출하면 프록시를 거치지 않아서 무의미하다.

## 5. readOnly = true의 의미

```java
@Transactional(readOnly = true)
public PostResponse getPost(Long id) { ... }
```

단순히 "읽기 전용 힌트"가 아니다. 실제로 일어나는 일:

- **Hibernate**: flush 모드를 `MANUAL`로 설정 → 영속성 컨텍스트의 dirty checking 스킵 → 성능 향상
- **DB Driver / Connection Pool**: 일부 드라이버는 read replica로 라우팅
- **JPA**: 스냅샷 저장 안 함 → 메모리 절약

조회 메서드에 `readOnly = true` 안 붙이면 dirty checking이 불필요하게 돌아간다.

## 6. Self-Invocation 함정 (이 프로젝트에서 실제 발생)

```java
@Service
public class QuestionService {

    public void outerMethod() {
        innerMethod(); // ← @Transactional 무시됨
    }

    @Transactional
    public void innerMethod() { ... }
}
```

`outerMethod()`는 프록시를 통해 호출되지만, 내부에서 `this.innerMethod()`를 호출하면 **프록시를 거치지 않고 원본 객체의 메서드를 직접 호출**한다.

이 프로젝트에서 `getQuestion`에 `@Transactional`이 없어서 `readOnly` 트랜잭션 내에서 쓰기 작업 시도 시 `TransactionRequiredException`이 발생했다. (커밋: `fix(qna): getQuestion에 @Transactional 추가`)

**해결책**:
- 메서드를 별도 빈으로 분리
- `ApplicationContext`에서 자기 자신을 주입받아 프록시 경유 (권장하지 않음)
- `@Transactional`을 클래스 레벨에 선언

## 7. 롤백 규칙

기본값: **`RuntimeException`과 `Error`만 롤백**, `CheckedException`은 롤백 안 함.

```java
// CheckedException → 롤백 안 됨 (기본값)
@Transactional
public void method() throws IOException { ... }

// 명시적으로 rollback 지정
@Transactional(rollbackFor = Exception.class)
public void method() throws IOException { ... }

// 특정 예외는 롤백 제외
@Transactional(noRollbackFor = OptimisticLockException.class)
public void method() { ... }
```

## 8. 트랜잭션과 영속성 컨텍스트(Persistence Context)

`@Transactional` 범위 = 영속성 컨텍스트 범위 (기본값, `OSIV=false` 기준).

- 트랜잭션 시작 → EntityManager 생성 → 영속성 컨텍스트 열림
- 트랜잭션 종료 → flush → commit → 영속성 컨텍스트 닫힘
- 트랜잭션 밖에서 지연 로딩(Lazy Loading) 시도 → `LazyInitializationException`

이 프로젝트는 `open-in-view: false` 설정 → Controller에서 지연 로딩 불가. Service 레이어에서 다 해결해야 한다.

## 9. 정리 — 면접 단골 질문 대응

**Q. @Transactional은 어떻게 동작하나요?**
> Spring이 CGLIB로 프록시 객체를 생성하고, TransactionInterceptor가 메서드 호출 전후에 트랜잭션 시작/커밋/롤백을 처리합니다.

**Q. Self-Invocation이 왜 문제인가요?**
> 같은 클래스 내 메서드 호출은 프록시를 거치지 않아 AOP 어드바이스가 적용되지 않습니다. `this` 참조가 프록시가 아닌 원본 객체를 가리키기 때문입니다.

**Q. readOnly = true를 왜 붙이나요?**
> Hibernate dirty checking과 스냅샷 저장을 생략해 성능을 높이고, DB 드라이버 레벨에서 read replica 라우팅 힌트를 줄 수 있기 때문입니다.
