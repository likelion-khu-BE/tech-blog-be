# 통합 이벤트 컨벤션

> BC 경계 넘는 통지(integration event)의 작성 규칙. 같은 BC 내 사이드 이펙트(domain event)는 이 컨벤션 대상 아님.

설계 배경: [ADR 0003](../adr/0003-외부-BC-통합-이벤트-방식.md)

## 핵심 원칙

**Consumer가 contract를 정의한다.** Consumer는 자기에게 어떤 필드가 필요한지 안다. Producer는 그 명세만 보장하면 됨 → producer가 자기 도메인을 자유롭게 진화시킬 수 있다.

## 위치

```
src/main/java/com/study/shared/extevent/
├── blog/
│   ├── README.md              # 이벤트 인덱스
│   └── BlogPostCreated.java
├── qna/
├── sessionboard/
└── profile/
```

- `extevent` = "external event": cross-BC 통합 이벤트. 다른 BC의 `domain/event/`(도메인 사건, 예: 행사)와 단어 충돌 회피
- `<BC>/`는 **publisher** BC 기준. consumer는 자유롭게 import

## record 작성

### 형태

```java
package com.study.shared.extevent.<publisher-bc>;

/**
 * (과거형 사실) — 한 줄.
 *
 * @param userId 활동 주체
 * @param xxxId  대상 식별자
 */
public record SomethingHappened(Long userId, Long xxxId) {}
```

### 네이밍

- `{대상}{Action-과거형}` 형식 — 예) `BlogPostCreated`, `QnaAnswerAccepted`
- 단어 충돌 시 BC prefix — `Question` 모호 → `QnaQuestionCreated`
- 과거형 사실. 명령형(`CreateBlogPost`) X

### 필드

- **식별자 위주** (`userId`, `xxxId`). 데이터 필요하면 consumer가 직접 조회
- **사실만**: 가공·집계·정책 결과(consumer 도메인 계산값) 박지 X — consumer마다 가공 방식 달라 contract 흔들림
- consumer가 정말 필요한 필드만. "혹시 모르니까" X

```java
// X — 엔티티 통째로 / 가공값
public record BlogPostCreated(BlogPost post, int score) {}

// O — 식별자만
public record BlogPostCreated(Long userId, Long postId) {}
```

## publish · listen

### Producer (publish)

`@Transactional` 메서드 안에서 발행:

```java
@Transactional
public BlogPost create(Long userId, ...) {
  BlogPost post = repository.save(BlogPost.create(...));
  eventPublisher.publishEvent(new BlogPostCreated(userId, post.getId()));
  return post;
}
```

### Consumer (listen)

```java
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onBlogPostCreated(BlogPostCreated event) {
  // 후처리
}
```

**두 어노테이션 둘 다 필수** — listener가 publisher에 피해 주지 않게:

- **AFTER_COMMIT**: publisher 트랜잭션 커밋된 뒤 실행 → listener 실패해도 publisher 데이터 유지 (롤백 X)
- **@Async**: 별도 스레드 → publisher 응답 시간 영향 X
- AFTER_COMMIT만 → 응답 시간 영향 남음 / @Async만 → 트랜잭션 경계 비결정적

`@Async` 활성화: `shared/config/AsyncConfig.java`. 자세한 비교: [ADR 0003 §Decision-4](../adr/0003-외부-BC-통합-이벤트-방식.md).

## 새 이벤트 추가 절차

Consumer 작업과 Producer 작업은 **시간적으로 안 묶임** — async + integration event의 강점. 머지 순서·PR 묶음 자유.

| | 작업 |
|---|---|
| **Consumer 측** | record + BC README 인덱스 + listener. PR review 시 producer에게 "이 필드 publish 가능?" 컨펌 |
| **Producer 측** | `eventPublisher.publishEvent(...)` 한 줄 추가 |

머지 순서 무관. listener는 이벤트 없으면 idle 상태로 대기.

## consumer는 producer를 신뢰하지 않는다

이벤트 패턴의 핵심 원칙: **검증은 consumer 측에서.** Producer는 단순 발행만.

이유: 서버가 클라이언트를 검증하는 것과 같은 사상. consumer가 record 의미 정의했으니 producer가 잘못 해석할 위험을 consumer가 방어해야 함. Producer에 검증 책임을 묶으면 BC 격리가 깨지고 producer 측에 부담이 누적됨.

### consumer 측 listener 권장 검증

- **input null/범위 체크** — producer가 잘못된 값 보낼 수 있다 가정
- **멱등성** — 같은 이벤트 두 번 와도 중복 처리 X (retry·outbox 도입 시 필수). unique constraint 또는 dedupe 로직
- **참조 무결성 검증** — `userId` 같은 키가 실제 존재하는지 (consumer 측 도메인 기준)

### producer 측은 단순하게

```java
@Transactional
public Xxx create(...) {
  Xxx xxx = repository.save(...);
  eventPublisher.publishEvent(new XxxCreated(...));   // 검증 X, 발행만
  return xxx;
}
```

publisher는 자기 도메인 트랜잭션 안에서 publish 한 줄만. 이벤트 의미 검증은 consumer가.

## 안 하는 것

| 안 함 | 이유 |
|---|---|
| producer가 임의로 record 작성 | consumer 요구 모름 → contract 흔들림 |
| producer 측에서 이벤트 의미 검증 | consumer 책임. producer는 단순 발행 |
| sync `@EventListener` 단독 | 트랜잭션 경계 미정 + publisher 응답 차단 |
| payload에 엔티티 통째로 | 결합도↑ — entity 진화 시 contract 깨짐 |
| payload에 점수·집계 등 가공 결과 | consumer마다 가공 방식 다름 |
| "혹시 모르니까" 필드 | 명세 비대화 — 의도 안 보임 |
| consumer listener에서 검증 생략 | producer를 신뢰하면 silent 오작동 |
