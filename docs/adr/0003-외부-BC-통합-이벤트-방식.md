# 0003. 외부 BC 통합 이벤트 방식

Date: 2026-05-03

## Status

Accepted

## Context

BC 간 데이터·사실을 옮길 방법이 필요하다. 한 BC에서 일어난 사건(엔티티 생성·수정·특정 상태 전이 등)을 다른 BC가 알아야 하는 일반 케이스.

| 후보 | BC 격리 | 오버헤드 | 발신 측이 수신 측 알아야? |
|---|---|---|---|
| **A.** 발신 측이 수신 측 빈 직접 호출 | 위반 | 0 | 알아야 함 (인터페이스 노출) |
| **B.** 발신 측이 수신 측 REST API 호출 | 유지 | HTTP 거침 | 알아야 함 (URL·계약) |
| **C.** Spring 통합 이벤트 (publish/listen) | 유지 | 0 (`ApplicationEventPublisher`) | 모름 |

→ **C 채택**. BC 격리 유지하면서 오버헤드 0이고, 발신 측이 수신 측 존재를 알 필요도 없는 유일한 안.

C로 정한 뒤 다음 의문: event record 누가 작성하나?

- producer-owned: 발신 측은 어떤 필드를 수신 측이 필요로 하는지 모른다
- **consumer-driven contract** ([Martin Fowler](https://martinfowler.com/articles/consumerDrivenContracts.html)): 수신 측이 필요를 명세, 발신 측은 그것만 보장

## Decision

### 1. Spring `ApplicationEventPublisher` 통합 이벤트

같은 BC 내 사이드 이펙트(domain event)와 구분되는 BC 경계 넘는 통지(integration event) — [Microsoft DDD](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation).

### 2. Contract는 consumer가 정의

Consumer가 record 작성, producer는 "이 필드 publish 가능?" 컨펌만. Producer가 자기 도메인 자유롭게 진화시켜도 명세된 필드만 보장하면 contract 안 깨짐.

Consumer 작업과 Producer 작업은 시간적으로 안 묶임 — async라 listener는 idle 상태로 대기 가능. 머지 순서 무관.

### 3. 위치: `shared/extevent/<BC>/`

- `extevent` = "external event": cross-BC 통합 이벤트. 다른 BC의 `domain/event/`(도메인 사건, 예: 행사)와 단어 충돌 회피
- `<BC>/` = 발행자 BC. 폴더 경로로 누가 publish하는지 보임

### 4. 실행: `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`

핵심: **listener가 publisher에 피해 주지 않게.**

| 옵션 | publisher 영향 |
|---|---|
| `@EventListener` (기본) | sync + 같은 트랜잭션. listener 실패 → publisher 롤백 |
| `@TransactionalEventListener(AFTER_COMMIT)` | publisher commit 뒤 실행. 데이터는 안전, **응답 시간엔 여전히 영향** |
| **AFTER_COMMIT + `@Async`** | 별도 스레드. 응답 시간 영향 X. **선택안** |

둘 다 필요한 이유: AFTER_COMMIT만 → 응답 시간 영향 남음. @Async만 → 트랜잭션 경계 비결정적.

### 5. Publisher는 사건과 이벤트의 1:1 대응 보장

비즈니스 commit 됐으면 이벤트는 빠짐없이 발행 — `eventPublisher.publishEvent(...)`를 같은 `@Transactional` 메서드 안에 둬서 트랜잭션 안전하게. **발행 자체를 취소하지 않음**: commit된 사건이 이벤트로 안 옴 = consumer 입장에서 "일이 없었던 게 됨" → 정합성 깨짐.

Publisher 측 검증은 자기 도메인 비즈니스 로직 직전(자기 도메인 보호용)만. 이벤트 의미 검증은 consumer 책임 (Decision §2).

## Consequences

**얻는 것**
- BC 격리 유지 — 발신 측은 수신 측 존재 모름
- 수신 측 정책·새 consumer 추가해도 발신 측 코드 0줄 변경
- 발신 측 흐름이 수신 측 실패에 막히지 않음

**트레이드오프** (의식한 선택)
- 처리 실패 silent — 강결합을 푼 대가. 복구 전략(아래) 단계적 도입
- 시맨틱 해석 오류 위험 — consumer가 record 의미 정의했으니, producer가 잘못 해석해서 publish하면 silent 오작동. async/sync 무관하게 본질적 위험. 보완: ① PR review에서 producer가 의미 컨펌, ② consumer는 producer를 신뢰하지 않고 listener에서 항상 검증
- async 테스트가 까다로움 (Awaitility 등 필요) — sync보다 신뢰성·격리 우선
- eventually consistent — 핵심 데이터 동기화(결제·재고)엔 부적합. outbox 패턴 등 별도 설계 필요

## 케이스별 결과

publisher commit과 listener 실행이 분리되어 각 케이스마다 결과가 다름:

| 시나리오 | publisher 데이터 | listener 작업 |
|---|---|---|
| publisher commit 성공 + listener 성공 | 저장 | 저장 |
| publisher commit 성공 + listener 실패 | 저장 | 미저장 (silent) |
| publisher commit 실패(rollback) | 폐기 | 호출 X (이벤트 폐기) |

→ "publisher 데이터는 저장됐는데 listener만 실패" 케이스만 정합성 깨짐 (silent). 나머지는 자연스럽게 처리.

## 처리 실패 시 복구 전략

잘못이 어디서 났는지에 따라 처리 방향이 다름. 두 갈래로 분리.

### Consumer 측 처리 실패 (listener 코드 버그·인프라 장애)

silent 케이스(publisher 성공 + listener 실패) 대응. 단계별 도입, 모두 소급 적용 가능 — 단계 추가 시 기존 listener 코드는 거의 안 바뀜.

| 단계 | 도입 트리거 | 방법 |
|---|---|---|
| **1 (현재)** | 기본 | listener 단순 throw + ERROR 로그 + alert. 운영자가 로그 보고 수동 보정 (DB 직접 INSERT 또는 재처리 스크립트) |
| **2** | 일시 장애(DB 단절·락 충돌 등)로 누락 잦음 | Spring Retry — `@Retryable` 자동 재시도. 영구 장애엔 무력 |
| **3** | 영구 장애로 누락 누적 | 정기 reconciliation batch — source(원본 데이터) vs derived(파생 데이터) 비교 후 누락 보정 |
| **4** | derived 데이터가 핵심으로 격상되거나 누락 0% 요구 | Outbox 패턴 — 이벤트를 DB outbox 테이블에 저장, 별도 worker polling/retry. 정합성 보장 |

단계 선택은 derived 데이터의 중요도와 누락 허용도에 따라.

### Publisher 측 잘못 (publish 누락·잘못된 데이터)

사후 보정보다 **사전 방지**에 의존. 발행 자체는 1:1 보장(Decision §5)이라 사후 취소·롤백 X.

| 케이스 | 처리 |
|---|---|
| **publish 누락** (코드에서 publishEvent 호출 빠짐) | Decision §5 "1:1 보장 룰"로 사전 방지 — `@Transactional` 메서드 안에 publish 강제. 사후 감지: reconciliation batch (consumer 측 3단계와 동일 메커니즘) |
| **잘못된 데이터로 publish** (예: 잘못된 userId) | consumer가 listener에서 식별 → ERROR 로그 + 책임자 추적. PR review에서 record 명세·publish 시점 사전 컨펌으로 방지 |

publisher 측 잘못은 본질적으로 **PR review와 컨벤션으로 잡는 영역**. 발행이 1:1로 보장되어야 consumer 측 복구 흐름(reconciliation 등)도 의미 있음.
